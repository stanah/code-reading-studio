# Code Reading Studio の検証マップ

このディレクトリは、Code Reading Studio の利用者に見える動作を検証するための、保守対象の手順集である。
画面を操作する前にこの索引を読み、該当する機能のファイルを手順として使う。

## 基本の前提

- リポジトリのルートで `STUDIO="node .claude/skills/verify-studio/scripts/studio.mjs"` を設定する。
- `$STUDIO launch` で新しい実行を起動し、`$STUDIO doctor` が `ok: true` を返すことを確かめる。
- データディレクトリは空から始まる。読解ノートは0件である。
- 読解対象は Reth v2.7.0（コミット `3d592ece6de8c4559987416a544fc215fd6d6921`）である。
- この実行が起動したインスタンス以外は操作しない。

## 操作の約束

- 各手順は、特に前提を書かない限り基本の状態から始める。
- 要素は ARIA の役割と名前で選ぶ。リンク名は部分一致で足りるが、同じ語を含むリンクが複数ある画面では `--exact` を付ける。
- コマンドは書かれたとおりに実行する。引用符の中の名前は変えない。
- 状態を変えた手順は、最後に元へ戻す（作ったノートは画面から削除する）。証拠は消さない。

## 証明とスキップの報告

- 操作とその結果の状態を残す。最後の画面だけでは足りない。
- 画面の証明は、ARIA スナップショットとスクリーンショットの組にする。
- 保存の証明には、`$STUDIO api GET /api/state` と、`$STUDIO restart` 後の画面表示を含める。
- 証拠には機能 ID と使った入口を記録する（ファイル名の先頭のディレクトリに機能 ID を使う）。
- 通せなかった入口は、試したコマンドと満たせなかった前提を報告する。
- 通せなかった入口を、別の入口で確かめたことにして報告しない。

## 機能ファイルの形

各ファイルは、H1 の機能名と、利用者に見える動作を述べる1段落で始まる。
続けて、次の4つの H2 をこの順に置く。

1. `Sub-features`：短い ID と、その動作を1行ずつ書く。
2. `How to get to it (user POV)`：利用者の入口をすべて書く。
3. `Driving it with studio.mjs`：`Preconditions:` で始め、利用者の操作、正確なコマンド、観察できる結果を組にした項目を並べる。
4. `Gotchas`：検証を無駄にしたり無効にしたりする落とし穴を書く。

実装の詳細はマップに書かない。
書くのは、利用者の経路、安定した操作手段、必要な状態、コマンド、観察できる証拠だけである。

## 機能

- [起動ガイド](./startup-guide.md)：全体像、段階、読みどころ、根拠のコードへの移動、ファイルからの逆引き。
- [ファイルから読む](./files.md)：ツリー、名前検索、行範囲の選択表示、400行ごとの移動、行へ移動。
- [読解ノート](./reading-notes.md)：行範囲へのメモ保存、再起動後の復元、削除、JSON 書き出し。
- [3つの見方と説明資料](./lenses.md)：構造から読む、送信経路を読む、Rust と設計、説明資料 `/guide`。
