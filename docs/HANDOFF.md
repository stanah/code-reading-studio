# 開発ガイド — Code Reading Studio

検証記録: 2026-10-18。検証範囲と残作業は9節。

## 1. 製品の目的

コードの理解と、画面共有による説明を支援する読解アプリ。
Rethを題材に、リポジトリの構造・動作・言語設計を段階的に探索する。

ガイドにはTypeScriptとの比較を用いたRustの入門解説を用意する。
原文コメントに加えて日本語の説明を提供し、処理の理解に必要な構文を段階的に示す。

設計要件:
- 全体像からいきなり実コードへ飛ばない。意味のある段階を踏んで詳細化する。
- 大量のコードを単なるファイル一覧にしない。
- 構造、アプリケーションの動作、言語ならではの設計を別々の見方として提供する。
- 画面を追加するたびにデザインを変えない。配色だけでなく、ナビゲーション・文字・余白・操作を一貫させる。

## 2. 読解体験

| 見方 | 段階 |
| --- | --- |
| 構造 | 全体の責務 → クレート・部品 → モジュール → 型・関数 → コード |
| 動作 | ユースケース → 大きな処理段階 → 部品間の受け渡し → 分岐・状態変化 → コード |
| Rust・設計 | 解決したい課題 → 日本語での意味 → TypeScriptの簡略例 → 類推の限界 → Rethでの効果 → コード |

選択した処理を維持したまま見方を切り替える。
動作の説明は呼び出し順だけでなく、データの変化・非同期の境界・待機・失敗・副作用を含める。
FutureとPromise、traitとinterfaceなどを同一視しない。TypeScript例は概念用で、等価な移植と誤認させない。
原文から確認できる事実、解説者やAIによる解釈、人がレビュー済みかを区別する。
現在のガイドは執筆済み解説であり、自動解析や実行トレースではない。

## 4. 実装の所在

現在はNode.jsと素のHTML/CSS/JavaScript。React・TypeScript化はまだ行っていない。
フレームワークの変更前に、既存機能と検証手順を確認する。

| パス | 内容 |
| --- | --- |
| local-app/core.mjs | Git固定コミットの索引・ソース取得・関数宣言候補・根拠ハッシュ・AIアダプター |
| local-app/server.mjs | localhost API・トークン/Origin/Host検証・JSON永続化・静的配信 |
| local-app/public/app.js | 段階的探索・行範囲選択・メモ・AI解説・JSON出力 |
| local-app/public/lenses.js | 動作/構造/Rustの3つの見方とTypeScriptを使った説明 |
| local-app/annotations.json | 固定コミット用の領域分類・モジュール説明・送信経路解説 |
| ui/studio.css, ui/studio.js | 共通デザインとナビゲーションの生成元 |
| ui/lenses-page.js | 静的ガイドから実コードへ進む際の対象・戻り先を保持する生成元 |
| scripts/build-design.py | 共通ファイルの配布と各HTMLへの共通ヘッダー組み込み |
| scripts/build-lenses.cjs | 静的ガイド用データ・共有画面コードの生成 |
| scripts/build-atlas.py, scripts/build-drill.py | Rethの索引・段階的読解用データ生成 |
| dist/index.html | 全体マップ・ファイル探索・読解キュー |
| dist/zoom.html | 段階的なモジュール/関数の読解 |
| dist/reader.html | コード・解説・読解ツアー・別窓共有 |
| dist/lenses.html | 3つの見方から入るガイド |
| docs/prototype-history.md | 静的ガイドの操作・仕様 |

共通ファイルのコピーを個別に直して再び分岐させない。
build-design.py は既存ヘッダーを検出するとHTML編集をスキップする実装なので、ヘッダーの継続更新が正しく反映されるか確認する。
build-lenses.cjs は local-app/public/lenses.js を静的版へコピーする。
dist/implementation.html は、このリポジトリとRethサブモジュールを取得して起動する手順を案内する。

## 5. 実装済みと制限

実装済み:
- 起動時にコミットを固定し、Gitの追跡済みソースを読み取る。
- 構造を段階的に探索する。必要なソースを取得し、限定的にキャッシュする。
- 行範囲、コード抜粋、ハッシュ、メモ、AI解説をJSONへ保存。再起動後の復元、削除、エクスポート。
- Rethの11責務領域と、トランザクション送信経路6箇所の説明。
- 動作を3つの大きな段階から個別処理へ展開する。
- 所有権と借用、Future、Result、trait、チャネルをTypeScriptとの比較で説明。
- 共通の明るい背景・緑のアクセント、共通ヘッダーとナビゲーションを適用。
- OpenAI互換Chat Completions APIへ選択範囲と質問を送信するアダプター。

制限:
- 関数抽出は行頭のfn宣言候補を拾う字句パターン。AST/LSP、マクロ展開、正確な関数終端、呼び出しグラフではない。
- 動作・日本語解説はトランザクション送信経路に限定。他の領域の意味を自動理解しているわけではない。
- 索引にファイルが存在することと、解説済み・理解済みであることは別。
- AI出力は未レビュー。コード範囲は保存するが、説明内容の正しさや引用との対応を自動検証していない。
- AIの実サービス接続は未検証。テスト用HTTPサーバーとの接続だけ検証済み。
- デスクトップの主要導線はブラウザーで実操作・目視確認済み（9節）。スマートフォン幅・全ページの見た目・勉強会での利用評価は未確認。
- local-appの発表表示は同じ画面の表示切替。dist/reader.htmlの別窓・BroadcastChannel同期と同じ機能ではない。
- 同じデータ保存先への複数プロセス同時書き込みは未対応。

送信経路:
1. RPC入口: crates/rpc/rpc-eth-api/src/core.rs
2. デコード・復元: crates/rpc/rpc-eth-api/src/helpers/transaction.rs
3. Ethereum向け実装: crates/rpc/rpc/src/eth/helpers/transaction.rs
4. 要求チャネル: crates/rpc/rpc/src/eth/core.rs
5. バッチ処理: crates/transaction-pool/src/batcher.rs
6. プール検証・追加: crates/transaction-pool/src/lib.rs

正常経路と、設定による外部転送・blob変換等を区別する。
戻り値のトランザクションハッシュは、ブロックへの取り込み完了やレシートではない。

## 6. 起動・検証

Node.js 22以上、Gitが必要。追加npmパッケージは不要。

```sh
git clone --recurse-submodules https://github.com/stanah/code-reading-studio-public.git
cd code-reading-studio-public
node local-app/server.mjs targets/reth 1a4dbbe11264fd52e6e9fbe768aa83f9a6b73607
```

http://127.0.0.1:4317 を開く。取得済みなら git submodule update --init --recursive で対象を取得する。

```sh
npm --prefix local-app test
node tests/smoke.cjs
node tests/atlas.cjs
node tests/zoom.cjs
```

local-appの8テストと、静的版3テストスクリプトが通過している。
Git固定コミット、許可パス、コード範囲、保存・再起動復元、AIアダプター、段階的な導線、エスケープ、発表時のメモ分離等を検証している。
画面系は偽DOMを使うロジックテストで、ブラウザーテストではない。開発環境で再実行する。

任意のAI設定:
- AI_BASE_URL: OpenAI互換APIのベースURL（例: http://127.0.0.1:1234/v1）
- AI_MODEL: 使用するモデル名
- AI_API_KEY: 必要な場合のみサーバー環境変数で設定
- READING_DATA_DIR: 保存先（既定 local-app/.reading-data）
- PORT: 既定4317

APIキーをブラウザーやGitに入れない。AI操作時に選択コード・質問等が設定先へ送信されることをUIで示す。
実プロバイダーが未設定なら「未設定」と記録し、テスト応答を実生成の成功として扱わない。

## 7. 検証と改善の優先順位

優先順位:
1. 現在のGit状態・ローカルの指示ファイルを確認し、サブモジュール取得、起動、既存テストを行う。
2. ブラウザーが利用できる環境で、ローカル版と静的版の実操作・見た目を確認する。
3. 確認した不具合を直す。特に共通ナビゲーション、見方の切り替え、実コードからの戻り、スマートフォン幅、文字の可読性を優先。
4. 設定済みの実AIサービスが使える場合に、選択範囲→解説→保存→再読込まで検証する。
5. その後、動作の図解・データの変化・非同期境界をより分かりやすくし、他のユースケースへ展開する。

受け入れ確認の例:
- Rust未経験者が「送信」を選び、大きな3段階→要求チャネル→入出力/分岐→Rustの説明→実コードへ迷わず進める。
- 「要求チャネル」の対象を保って、構造・動作・Rustを行き来できる。
- TypeScriptの例がRethの実コードと明確に区別される。
- 全体マップ、段階的読解、コード画面、言語ガイドで共通の視覚と操作が保たれる。
- 保存した範囲とメモが再起動後も同じコミットの同じコードに対応する。

ブラウザーや実AIが使えない場合は、未検証の範囲と理由を明記する。
次の機能追加を急いで、全体像からコードへ飛ぶ導線や別デザインの画面を増やさない。

## 8. リポジトリに記載する情報

ドキュメント・コード・コミットメッセージには公開可能な製品・技術情報のみを記載する。
個人のプロフィールや好み、非公開の会話、内部の接続先・認証情報、個人用データを転記しない。
説明例には架空のデータまたは公開されている資料を用いる。
